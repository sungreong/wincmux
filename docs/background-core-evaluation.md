# 백그라운드 실행 코어 평가 — 0.2.0

## 측정 조건

동일 Windows x64 PC에서 기존 0.1.4와 백그라운드 코어를 분리한 0.2.0을 각각 세 번 실행했다. 아래 비교는 **UI 디자인 변경 전 동일한 화면 구성**에서 수행한 코어 분리 비교이며, 이후 프론트 디자인 변경의 성능 결과와 구분한다. 값은 세 번의 중앙값이다.

테스트 CLI는 Node 기반 ConPTY fixture이며 실제 Codex·Claude의 모델 응답이나 메모리 사용을 측정한 것이 아니다. 앱 메모리는 UI·전용 WebView2·독립 코어의 전용 메모리 합계이며 CLI 메모리는 제외했다. 별도 코어 PID를 집계하여 UI의 부모 프로세스 트리에서 분리된 경우에도 누락하지 않았다. 화면 크기가 안정된 후 1개/6개 패널에서 3,000/18,000줄의 원문 일치와 30회 입력 왕복을 확인했다.

| 항목 | 0.1.4 | 0.2.0 |
|---|---:|---:|
| 1개 · 앱·코어 전용 메모리 | 312.24 MiB | 323.51 MiB |
| 1개 · 입력 왕복 P95 | 17.20 ms | 13.00 ms |
| 1개 · 출력 표시 시간 | 261.00 ms | 246.00 ms |
| 6개 · 앱·코어 전용 메모리 | 385.99 MiB | 396.34 MiB |
| 6개 · 입력 왕복 P95 | 15.90 ms | 15.60 ms |
| 6개 · 출력 표시 시간 | 507.00 ms | 594.00 ms |

6개 패널의 앱·코어 메모리 중앙값 증가는 **10.35 MiB**다. 입력 왕복 P95 중앙값은 기존 15.90ms, 분리 후 15.60ms다. 일반 PC의 백그라운드 부하와 숨김 창의 스케줄링에 따라 개별 측정은 변동한다.

## 화면 종료 후 자원

- 실제 네이티브 트레이를 켠 코어, 테스트 터미널 6개, WebView2 없음: **6.94 MiB**.
- 같은 조건의 60초 유휴 CPU: **0.155%**. 프로세스 CPU 시간/경과 시간으로 계산했으며 논리 CPU 수로 나누지 않았다.
- 50회 IPC 클라이언트 연결·구독·해제: 전용 메모리 5.21 → 4.92 MiB, 핸들 173 → 173개.
- 화면 수명 테스트 세 번 모두 일반 종료·강제 종료 후 기존 코어 및 작업 PID 유지, 해당 UI의 WebView2 프로세스 종료를 확인했다.

## 기능 검증

Rust 테스트 18개, JS 어댑터 테스트 2개, 실제 프로세스 통합 테스트 3개, UI 회귀 테스트와 3회 화면 수명 테스트를 수행했다. 한글·연속 공백·여러 줄 초안·복사·분할·출력 원문을 확인했다.

출력 보관 범위를 넘긴 대체 화면을 재실행 후 복원하고, 정상 화면으로 돌아왔을 때 기존 내용과 붙여넣기 모드가 보존되는 것을 확인했다. 숨긴 세션·미확인 결과도 유지되며, 알림으로 숨긴 터미널을 다시 열 수 있다. 코어 종료 후 저장된 알림 URI로 새 코어를 열어 기록을 확인하더라도 작업은 자동 재실행되지 않는다.

실행 중인 작업이 있을 때 업데이트 준비 거부, 예약 중 새 코어 시작 차단, 예약 취소, 중복 코어 거부, 코어 충돌 시 Job Object 자식 종료, 빈 코어의 30초 자동 종료, 출력 중 resize를 확인했다. 설치기는 빌드 및 사전 검사 순서를 검증했으며 현재 사용자의 설치·레지스트리를 실제로 교체하지 않았다. 설치된 URI의 실행 경로는 UUID 파싱과 새 UI 프로세스 기동으로 검증했다.

## 재현

```powershell
npm run package:win
npm run lint
npm test
npm run test:runtime
npm run test:ui
npm run test:lifecycle
```

Windows에서는 실행 중인 개발 코어의 실행 파일을 덮어쓸 수 없으므로 빌드와 프로세스 테스트를 순서대로 실행한다. 개별 측정 JSON과 스크린샷은 로컬 `artifacts/background-core/`에 보관하며 저장소에는 포함하지 않는다.
